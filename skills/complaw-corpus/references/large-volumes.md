# Тома в несколько тысяч страниц

Написано по разбору Koller/Lovrek/Spitzer, Insolvenzordnung², Verlag Österreich 2023: 3727 страниц файла, 8774 карточки, четыре комментируемых акта в одном томе. Всё ниже — не теория, а грабли, на каждые из которых наступили.

На таком объёме меняется не масштаб, а список отказов. Книга на семьсот страниц прощает неаккуратность: неверный параметр даёт полсотни кривых карточек, они видны в отчёте, прогон повторяется за минуту. Том на три с половиной тысячи страниц наказывает иначе — прогон стоит десять минут, дефект даёт тысячу карточек, а часть отказов вообще не сообщает о себе.

## Разбор страниц — кусками, и никак иначе

`pages_digital.py` на трёх с половиной тысячах страниц **умирает молча**, не дойдя до конца. У `pdfplumber` разобранные страницы остаются в памяти, и на таком томе её съедает целиком; процесс убивает ядро, а не исключение, поэтому в журнале нет ни трассировки, ни последней строки — только оборванный счётчик.

Поэтому диапазон режется на куски по 1500–2000 страниц, каждый заход — отдельный процесс:

```bash
for R in 70-1900 1901-3629; do
    python scripts/pages_digital.py книга.pdf --book books/<id> \
        --profile profiles/<профиль>.yaml --pages $R --skip-done
done
```

`--skip-done` здесь обязателен, и не ради скорости: последний заход собирает `work/pages.jsonl` из **всего** накопленного кэша, а не только из своего диапазона. Без него второй кусок молча выбросит первый.

Постраничный кэш переживает падение, так что цена ошибки — только остаток. На упомянутом томе первый заход умер на 3204-й странице из 3560, второй доделал остаток за сорок секунд.

## Код возврата не прятать за конвейером

```bash
python scripts/pages_digital.py … 2>&1 | tail -4      # так нельзя
```

Код возврата конвейера — это код `tail`, то есть всегда ноль. Убитый по памяти python выглядит как успех, а отсутствие `pages.jsonl` замечается через полчаса. Писать в файл и смотреть код явно:

```bash
python scripts/pages_digital.py … > pages.log 2>&1; echo "код: $?"; tail -3 pages.log
```

Признак успеха — строка «Страниц в модели: N», а не молчание.

## Ветка B на таком томе не идёт

Один проход tesseract по плотной странице комментария — 2–3 минуты, а пайплайн гоняет до четырёх вариантов на страницу. Три тысячи страниц — это сотни часов. Считать это **до** запуска, а не после.

Ветка B на большом томе годится только точечно: по страницам с дырами в нумерации, по срезу для сверки. Если паспорт говорит «ветка B» на трёх тысячах страниц — это разговор с человеком о времени и о том, где взять машину, а не фоновая задача.

## Многоактный том: код акта входит в адрес

Комментарии часто выпускают одним томом сразу к нескольким законам. У упомянутого тома их четыре: IO, ReO, EKEG, EuInsVO. Нумерация параграфов в каждом своя и начинается с единицы, поэтому **«§ 1» существует в трёх экземплярах**, а всего пересечений полсотни.

Что происходит, если этого не заметить: `external_id` двух разных карточек совпадает, и при загрузке (она идемпотентна по `external_id`) одна затирает другую. Корпус молча худеет, отчёт о качестве ничего не показывает — номера-то не дублируются внутри своего акта.

Границы актов берутся из узлов верхнего уровня зашитого оглавления. Оформление адреса — **по конвенции самой книги**, а не по своему вкусу; она видна в колонтитуле: у основного акта код обычно не пишется («§3 Kodek»), у остальных пишется после номера («§7 ReO Reisch», «Art45 EuInsVO Weber-Wilfert»).

Проверка одна и жёсткая: после присвоения адреса пересчитать `external_id` и убедиться, что столкновений **ноль**. Не «мало», а ноль.

## Граница раздела проходит по строке, а не по странице

Режим `section: outline` переключает раздел на всю страницу, где стоит узел оглавления. В комментарии это неверно: комментарий к § 1 кончается в середине той полосы, где начинается § 2. Сверху страницы идут Rz 42–43 предыдущего параграфа, ниже — заголовок «§ 2. (1) …».

Хвост предыдущего параграфа получает чужой адрес и сталкивается по id с настоящими Rz 42–43 следующего. На упомянутом томе так набралось 846 столкновений.

Лечится сдвигом точки переключения внутрь страницы: список параграфов берётся из оглавления (он авторитетный), а тело используется только чтобы найти, **где именно** на полосе стоит заголовок нужного параграфа. Не нашёлся — переключаемся по странице, как раньше, и это видно в отчёте.

Отдельным адресом получает вводный комментарий «Vor § 1»: это самостоятельная единица цитирования со своей нумерацией Rz, и без своего адреса она сталкивается с настоящим § 1.

## Оглавление раздела притворяется номерами единиц

У каждого параграфа своё оглавление (Inhaltsübersicht): строки с отточием, справа номер Rz. Этот номер садится **ровно в коридор маргиналий** — визуально он там и стоит. В результате каждый параграф получает дубли своих же первых Rz; на упомянутом томе это 692 карточки-призрака и почти все столкновения id.

Отличить по положению нельзя, по кеглю в профиле — тоже. Зато сама строка опознаётся безошибочно: она полна отточия. Это `junk.patterns`, и снимается она до нарезки:

```yaml
junk:
  patterns:
    - '\.\s?\.\s?\.\s?\.\s?\.'
```

Проверить, что в прозе книги пяти точек подряд не бывает; многоточие из трёх точек под паттерн не попадает.

## `margin.scope: book` для издательского файла

По умолчанию полоса набора меряется на каждой странице. На книжном скане это правильно, а на ровном издательском файле — вредно: на первой странице каждого параграфа текст закона набран с отступом, медиана уезжает, и цифры самого закона («1.», «2.», «3.» перечисления) попадают туда, где постранично ожидается поле. Получаются карточки из текста закона, а не из комментария.

`scope: book` ищет коридор маргиналий по всей книге сразу. На упомянутом томе это убрало 37 таких карточек и снизило столкновения с 40 до 4.

Порядок важен: сначала junk-паттерн на отточие, потом `scope: book`. Иначе номера из оглавлений параграфов сами формируют «коридор» и портят общую статистику.

## Знак сноски — конвенция издательства, а не константа

Пайплайн ждёт знак со скобкой или точкой («29)», «29.»). Verlag Österreich ставит голое число:

```
29 DazunäherKodekinKonecny,Insolvenz-Forum2003,19.
```

Ни один знак не читается, вся полоса сносок страницы ложится **одним блоком без номера**. Внешне это почти незаметно: в отчёте «блоков сносок без читаемых номеров» — строка, на которую легко не посмотреть. Но при загрузке такие сноски отсеиваются (в схеме приёмника номер обязателен и целочисленный), и книга приезжает в базу без аппарата. На упомянутом томе так терялось 19 тысяч сносок из 19,4 тысяч.

Голое число само по себе слишком слабый признак: немецкие и австрийские сноски набиты номерами дел вида «5 Ob 142/68», «3 Ob 627/82», и они начинают строку точно так же. Рабочее правило — **монотонность**: номер принимается, только если он больше предыдущего принятого на этой же странице. Номер дела попадает в диапазон случайно и, как правило, вниз.

Смотреть на строку «Блоков сносок без читаемых номеров» в каждом отчёте. Если она сравнима с числом страниц — знак не читается вообще, и дело в конвенции издания.

## Управляющие символы из оглавления PDF

Заголовки в зашитом оглавлении бывают набиты хвостами `\x00` (выравнивание до фиксированной длины). В карточку они попадают через `hierarchy`, а Postgres не принимает ` ` в `text`/`jsonb` и отвечает **голой 500 без объяснения** — первая же пачка ложится, в базе ноль.

Чистить управляющие символы у себя, пока карточка своя. Диагностика в одну строку:

```python
re.search(r'[\x00-\x08\x0b\x0c\x0e-\x1f]', json.dumps(card, ensure_ascii=False))
```

## Предел на тело запроса при загрузке

Перед сервисом обычно стоит обратный прокси со своим пределом на тело (у nginx по умолчанию 1 МБ). Пачка из 64 карточек с векторами на 1536 весит около двух мегабайт и отбивается 413, причём ответ приходит от прокси, а не от сервиса, и в нём нет ничего полезного. Предел заранее не виден, поэтому его нащупывают: пачка делится пополам, пока не пройдёт, найденный размер запоминается на остаток загрузки.

Заливка большого тома идёт десятки минут — вести файл состояния с уже загруженными `external_id`, чтобы обрыв не начинал сначала.

## Метрики отчёта после своей постобработки

Если адрес карточки менялся своим скриптом (дописан код акта, переименован раздел), часть метрик отчёта перестаёт значить то, что написано. Живой пример: «внутренние отсылки разрешаются 84.8%» — отчёт сверяет отсылку «§ 149 Rz 6» с полем `section`, а там уже стоит «IO 149». Прямая сверка по тройке (акт, параграф, номер) дала 99.1%.

Правило: **метрика, посчитанная не по тем полям, хуже отсутствующей** — она выглядит как найденный дефект и уводит время. Если постобработка меняет поля, по которым считается метрика, пересчитать её самому и сказать в отчёте, какая цифра настоящая и почему.

## Порядок работы с большим томом

1. Паспорт. Оценить время ветки B **до** выбора ветки.
2. Профиль. Заложить `scope: book` для издательского файла и junk-паттерн на отточие, если у разделов есть свои оглавления.
3. Страницы кусками по 1500–2000, `--skip-done`, код возврата смотреть явно.
4. Пробная нарезка. Сразу проверить три вещи: столкновения `external_id`, «блоков сносок без читаемых номеров», управляющие символы.
5. Постобработка адреса, если том многоактный или граница раздела режется по странице.
6. Отчёт о качестве. Метрики, задетые постобработкой, пересчитать самому.
7. Проекция, загрузка с файлом состояния, независимая проверка поиском.
8. Журнал решений: на таком томе через неделю не вспомнить, почему `scope: book` и откуда взялся junk-паттерн.
