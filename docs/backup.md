# Резервное копирование

Корпус собирался год, а живёт он на одной машине в Хельсинки. Ниже — что
именно ценно, где оно лежит вторым экземпляром и как это восстановить.

## Что чем восполняется

| Что | Где ещё есть | Восполнимо |
|---|---|---|
| Карточки 38 книг (57 278) | `books/*/output/cards.jsonl.gz` в этом репозитории, GitHub | Да: перенарезкой из PDF по профилю |
| **31 источник австрийского корпуса (31 912 чанков)** | `archive/service-only/` — и больше нигде | **Нет.** Ни каталога в `books/`, ни профиля, ни PDF |
| Эмбеддинги (89 190 × 1536) | только в базе | Да: пересчётом из текста, см. ниже |
| Реквизиты источников | `archive/sources.json` | Да, но вручную |
| PDF-исходники (1.6 ГБ) | Hetzner Object Storage (см. `S3_*` в `.env.example`), Google Drive у владельца | Нет, если пропадут обе копии |
| Код сервиса и пайплайна | GitHub + `service-system-files.tar.gz` на Drive | Да |
| Секреты (`.env` на машине) | **менеджер паролей владельца** | Нет |

Главная дыра была одна — тридцать один источник, заведённый до нынешнего
пайплайна. Он закрыт: `archive/service-only/` в репозитории.

## Три уровня, и зачем их три

**1. Ночная копия на Drive — `scripts/backup_db.sh`, на машине сервиса.**
Отвозит в папку три файла: дамп базы (`pg_dump -Fc`), архив кода без `.env`
и `git bundle` всего репозитория с историей. Только этот уровень берёт
эмбеддинги: API их не отдаёт вовсе, а 89 тысяч векторов по 1536 чисел через
HTTP тащить и незачем. Восстанавливается одной командой, целиком или по
таблицам. Это и есть настоящий бэкап; остальное — страховка к нему.

Почему именно сервер, а не агент: агент ходит в сервис по HTTP и файл на
Drive кладёт через переписку — сотни мегабайт так не проходят, да и
побайтная точность двоичного архива при таком переносе не гарантирована.

Ставится на cron там же:

    0 3 * * * cd /opt/corpus && ./scripts/backup_db.sh >> /var/log/corpus-backup.log 2>&1

**2. Читаемая выгрузка — `scripts/backup_corpus.py`, откуда угодно.**
Ходит по API и складывает текст, иерархию, страницы и сноски в JSONL по
файлу на источник. Дамп нельзя открыть глазами и нельзя частично забрать;
эту выгрузку — можно, и она переживёт смену СУБД. Эмбеддингов в ней нет.

**3. Репозиторий.** Карточки книг и `archive/service-only/` лежат в git и
уезжают на GitHub при каждом `push`. Это то, что не зависит ни от машины
сервиса, ни от Drive.

## Пересчёт эмбеддингов

Пугаться потери векторов не стоит. Весь корпус — около 29 миллионов токенов;
по цене `text-embedding-3-small` это меньше доллара и несколько часов машинного
времени. Порядок: `scripts/reupload_all.py` для книг,
`scripts/reflow_service_source.py` + `upload_corpus.py` для источников из
`archive/service-only/`.

## Секреты на Drive не кладутся

В папку резервных копий уходят код, тексты и дампы. `.env` — не уходит:
в нём `API_TOKEN`, `OPENAI_API_KEY`, пароль Postgres, пароли веб-интерфейса
и `MCP_ACCESS_TOKEN`, а папка расшарена ссылкой. Вместо значений
резервируется `.env.example` — там перечислены все переменные и сказано, чем
каждую заполнить. Сами значения живут в менеджере паролей.

Отдельно: `API_TOKEN` однажды попал в переписку. Пока он не сменён в `.env`
и `api` не перезапущен, считать его тайной нельзя.

## Восстановление с нуля

1. `git clone` репозитория, `cp .env.example .env`, заполнить значения.
2. `docker compose up -d --build` — `entrypoint.sh` прогонит `alembic upgrade head`.
3. Если есть дамп: `gunzip -c corpus-<штамп>.dump.gz | docker compose exec -T db pg_restore -U corpus -d corpus --clean --if-exists`. На этом всё.
4. Если дампа нет: завести источники по `archive/sources.json`, затем
   `scripts/reupload_all.py` (книги) и выгрузка из `archive/service-only/`.
   Эмбеддинги посчитаются заново.
