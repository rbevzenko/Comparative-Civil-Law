# Comparative Civil Law — сервис хранения корпуса

Слой хранения и выдачи данных для корпуса сравнительного частного права:
хранит исходные PDF книг (в объектном хранилище), хранит их разбор на
цитируемые фрагменты («чанки») с гибридным поиском (вектор + полный текст),
отдаёт данные через HTTP API и даёт веб-интерфейс с логином по паролю для
загрузки источников/чанков и проверки качества загруженных данных.

Разбор PDF на чанки и понятийная разметка — отдельные задачи, в этом
репозитории не реализованы: `POST /sources/{id}/chunks` — точка входа,
которой пользуется внешний скрипт нормализации. MCP-сервер (`/mcp`)
реализован — тонкая обёртка над `/search` и `/chunks/{id}` для подключения
корпуса как custom-коннектора в Claude.ai (см. «MCP-сервер» ниже).

## Стек

- **API**: Python 3.12, FastAPI, SQLAlchemy 2 (async), Alembic
- **БД**: PostgreSQL 16 + `pgvector` (HNSW-индекс для векторного поиска,
  `tsvector`/GIN — для полнотекстового)
- **Хранение PDF**: S3-совместимое объектное хранилище (Hetzner Object
  Storage). PDF никогда не хранятся в Git или в самой БД; API отдаёт только
  presigned-ссылки, не раздаёт файлы напрямую
- **Веб-интерфейс**: Jinja2, без JS-фреймворков — работает в том же
  FastAPI-процессе, что и API (см. «Архитектурное решение» ниже); вход по
  паролю (сессионная кука), включает формы загрузки источника и чанков
- **MCP**: официальный Python SDK (`mcp`), Streamable HTTP — та же точка
  входа, что и у Claude.ai custom-коннекторов
- **Развёртывание**: Docker Compose (`db`, `api`, `caddy` — TLS для `/mcp`)

### Архитектурное решение: `api` и `web` в одном сервисе

Спецификация допускает вынос `web` в отдельный сервис "при необходимости".
Здесь необходимости нет: сервер — Hetzner CPX22 (2 vCPU / 4 ГБ RAM), и
запускать второй Python-процесс со своим пулом соединений к БД ради трёх
read-only страниц не оправдано. Веб-интерфейс — это отдельный APIRouter
(`app/web/router.py`), подключённый в `app/api/main.py` под префиксом
`/ui`, использующий тот же async-движок SQLAlchemy. При росте нагрузки
вынести его в отдельный контейнер — вопрос добавления второго `build` в
docker-compose.yml, код менять не придётся.

## Схема данных

- **sources** — книги/источники: метаданные + `pdf_object_key` (путь в
  object storage; сам файл в БД не хранится)
- **chunks** — фрагменты текста с готовой цитатой, номером пункта/Randnummer,
  иерархией разделов (`hierarchy jsonb`), диапазоном страниц, эмбеддингом
  (`vector(1536)` — см. ниже), заделом на будущий глоссарий (`concept_ids`) и
  опциональным `external_id` (стабильный id из внешнего пайплайна нарезки —
  обеспечивает идемпотентность повторной загрузки, см. раздел API)
- **footnotes** — сноски, привязанные к чанку

Индексы: HNSW на `chunks.embedding` (cosine), btree на `chunks.source_id` и
`sources.jurisdiction`, GIN по `chunks.text_tsv` (генерируемая колонка,
`to_tsvector('simple', text)` — конфигурация `simple` выбрана намеренно:
корпус многоязычный, единая стемминг-конфигурация исказила бы большинство
языков).

### Про размерность эмбеддинга

`chunks.embedding` — `vector(1536)`, зафиксировано в
`app/api/models/chunk.py::EMBEDDING_DIM` и в первой Alembic-миграции (pgvector
требует фиксированную размерность для HNSW-индекса). 1536 — размерность
OpenAI `text-embedding-3-small`/`text-embedding-ada-002`, разумное значение
по умолчанию. Если пайплайн нормализации будет использовать другую модель
эмбеддингов с другой размерностью, нужно одновременно поменять константу и
накатить новую миграцию (`ALTER COLUMN ... TYPE vector(N)` + пересборка
HNSW-индекса) — это единственное место, где размерность зашита.

**API не считает эмбеддинги.** `POST /sources/{id}/chunks` ожидает готовый
вектор в теле запроса — это забота внешнего скрипта нормализации, не сайта.

## Развёртывание

### 1. Подготовить окружение

```bash
cp .env.example .env
```

Заполнить `.env`:

| Переменная | Назначение |
|---|---|
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` | учётные данные Postgres |
| `DATABASE_URL` | `postgresql+asyncpg://<user>:<password>@db:5432/<db>` — используется api-контейнером |
| `API_TOKEN` | bearer-токен для всех эндпоинтов API, кроме `/health`. Сгенерировать: `python3 -c "import secrets; print(secrets.token_urlsafe(32))"` |
| `S3_ENDPOINT_URL`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_BUCKET_NAME` | доступ к Hetzner Object Storage (или любому S3-совместимому хранилищу) |
| `S3_PRESIGNED_URL_EXPIRY_SECONDS` | время жизни presigned-ссылки на PDF (по умолчанию 3600) |
| `UI_PASSWORD_1`, `UI_PASSWORD_2` | два независимых пароля для входа на `/ui/*` (любой из них подходит) — сгенерировать: `python3 -c "import secrets; print(secrets.token_urlsafe(16))"` |
| `SESSION_SECRET_KEY` | подписывает сессионную куку после входа — сгенерировать: `python3 -c "import secrets; print(secrets.token_urlsafe(32))"` |
| `DB_POOL_SIZE`, `DB_MAX_OVERFLOW` | размер пула SQLAlchemy (небольшой по умолчанию — учитывает лимит RAM) |
| `MCP_DOMAIN` | домен, для которого `caddy` получает сертификат Let's Encrypt — свой или `<ip-через-дефисы>.sslip.io` |
| `MCP_ACCESS_TOKEN` | токен для URL коннектора `/mcp` — сгенерировать: `python3 -c "import secrets; print(secrets.token_urlsafe(32))"` |
| `OPENAI_API_KEY` | опционально — включает векторную часть поиска в MCP (без него `search_corpus` ищет только по тексту) |

Бакет в Hetzner Object Storage нужно создать заранее (через Hetzner Cloud
Console или `s3cmd`/`aws-cli` с указанным endpoint) — сервис его не создаёт.

### 2. Поднять сервисы

```bash
docker compose up -d --build
```

Миграции Alembic применяются автоматически при старте контейнера `api`
(см. `docker/entrypoint.sh`: `alembic upgrade head` перед запуском uvicorn).
Расширение `vector` создаётся при первой инициализации `db` (`init.sql`) и
повторно, идемпотентно, первой миграцией — на случай, если база
создавалась не через этот compose-файл.

Проверить, что всё поднялось:

```bash
curl http://localhost:8000/health
```

Для `caddy` (нужен для `/mcp`) в файрволе должен быть открыт порт `443`.
Порт `80` (`docker-compose.yml`) сознательно не проброшен — сертификат
получается через TLS-ALPN-01 (`Caddyfile`: `disable_http_challenge`), а не
через обычный HTTP-01, именно чтобы не конфликтовать с чем-то ещё, что уже
слушает 80 на хосте (веб-панель, другой nginx и т.п.). Если 80 у вас
свободен и такого конфликта нет — можно вернуть `disable_http_challenge` и
проброс `"80:80"`, оба способа рабочие.

Проверить внешнюю доступность:

```bash
curl https://<MCP_DOMAIN>/health
```

Если Caddy не может получить сертификат — почти всегда порт `443` закрыт
снаружи или `MCP_DOMAIN` не резолвится в IP сервера; смотреть
`docker compose logs caddy`.

### 3. Применить миграции вручную (если нужно)

```bash
docker compose exec api alembic upgrade head
docker compose exec api alembic revision --autogenerate -m "..."   # при изменении моделей
```

## API

Все эндпоинты, кроме `/health`, требуют заголовок:

```
Authorization: Bearer <API_TOKEN>
```

### Служебный контур (загрузка / просмотр)

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/sources` | Регистрация источника: `multipart/form-data` с метаданными (`title`, `jurisdiction`, `source_type`, `authors` — через `;`, `edition`, `year`, `publisher`, `language`, `pdf_pages_total`) и файлом `pdf`. Загружает PDF в object storage, возвращает `source_id` |
| `GET` | `/sources?jurisdiction=&source_type=&limit=&offset=` | Список источников с фильтрами |
| `GET` | `/sources/{id}` | Метаданные источника + `pdf_url` (presigned, временная) |
| `POST` | `/sources/{id}/chunks` | Пакетная загрузка чанков: `{"chunks": [...]}`, каждый чанк включает готовый `embedding` (список из 1536 float) и опционально вложенные `footnotes` |
| `GET` | `/sources/{id}/chunks?limit=&offset=` | Список чанков источника — для проверки качества нарезки |

**Идемпотентная загрузка.** Каждый чанк может нести `external_id` — стабильный id из
внешнего скрипта нормализации (например, `"book_id-unit"` у чанкера). Если он указан,
повторная загрузка того же файла для того же источника **обновляет** совпавшие по
`external_id` чанки (текст, цитату, эмбеддинг, сноски — целиком), а не создаёт дубли.
Это регулируется уникальным ограничением `(source_id, external_id)` в БД — см.
`app/api/services/chunks.py::create_chunks`. Чанки без `external_id` всегда
вставляются как новые строки: сопоставлять их не с чем, и по умолчанию так было
раньше, до появления этого поля.

### Поисковый контур (используется и JSON API, и MCP-сервером)

| Метод | Путь | Назначение |
|---|---|---|
| `GET`/`POST` | `/search` | Гибридный поиск: полнотекст (`ts_rank` по `simple`-конфигурации) + опционально вектор (cosine, если передан `embedding`), объединение через Reciprocal Rank Fusion. Параметры: `q`, `jurisdiction`, `source_type`, `embedding` (JSON-массив float), `limit`, `offset` |
| `GET` | `/chunks/{id}` | Полный чанк по id, со сносками и метаданными источника |

`GET /search` существует ради соответствия исходному ТЗ и подходит для
чисто лексических запросов; `embedding` как query-параметр — это JSON-массив
из ~1536 чисел, что на практике длиннее типичных лимитов на длину URL у
прокси. Для гибридного поиска с реальным вектором предпочтителен
`POST /search` с тем же телом в JSON — эндпоинт с тем же поведением,
добавлен как практическое расширение спецификации.

Если `q` пустой и `embedding` не передан — 422. Если передан только `q` —
поиск чисто лексический. Векторную часть эмбеддинга запроса API не считает
сам: как и на запись, это внешняя ответственность (будущий MCP-сервер или
скрипт нормализации, который знает, какой моделью считать эмбеддинги).

Полная OpenAPI-схема — на `/docs` (Swagger UI) при запущенном сервисе.

## MCP-сервер (`/mcp`)

Тонкая обёртка над `/search` и `/chunks/{id}` по протоколу [MCP](https://modelcontextprotocol.io/)
(Streamable HTTP), смонтированная в тот же FastAPI-процесс (`app/mcp/`,
подключается в `app/api/main.py`). Даёт два инструмента:

- `search_corpus(query, jurisdiction?, source_type?, limit?)` — гибридный
  поиск; если задан `OPENAI_API_KEY`, запрос эмбеддится
  `text-embedding-3-small` перед вызовом `run_search`, иначе поиск чисто
  полнотекстовый
- `get_chunk(chunk_id)` — полный текст фрагмента по id из результатов поиска

Оба инструмента и роутер `/search`/`/chunks` используют одну и ту же
сервисную логику (`app/api/services/search.py`, `app/api/services/chunks.py`)
— MCP ничего не дублирует, только форматирует результат в текст для модели.

**Авторизация.** У Claude.ai в диалоге добавления custom-коннектора нет поля
для bearer-токена или заголовка — только URL. Поэтому токен передаётся как
query-параметр прямо в адресе коннектора: `https://<домен>/mcp?token=<токен>`
(проверяется в `app/mcp/auth.py`; `Authorization: Bearer` тоже принимается —
для локальных клиентов). Держите этот URL в секрете так же, как пароль.

**HTTPS обязателен.** Удалённые коннекторы Claude.ai требуют, чтобы сервер
был доступен по HTTPS с валидным сертификатом — просто `http://<ip>:8000`
не подходит. Поэтому перед `api` поставлен `caddy` (см. `docker-compose.yml`,
`Caddyfile`), который сам получает сертификат Let's Encrypt для домена из
`MCP_DOMAIN`. Если своего домена нет, подойдёт бесплатный
`<ip-через-дефисы>.sslip.io` (например, `37.27.248.75` → `37-27-248-75.sslip.io`)
— это настоящая публичная DNS-запись, wildcard-домен без регистрации, Let's
Encrypt с ним работает как с обычным доменом.

## Веб-интерфейс

Вход на `/ui/login` — форма с паролем (любой из `UI_PASSWORD_1` /
`UI_PASSWORD_2`), после успешного входа — сессионная кука на 14 дней. Все
страницы `/ui/*`, кроме самого логина, требуют сессию и без неё
редиректят на `/ui/login?next=...`.

Страницы:

- `/ui/` — дашборд: сколько источников/чанков/сносок/юрисдикций в корпусе,
  разбивка по юрисдикциям, недавно добавленные источники
- `/ui/sources` — список источников с фильтром по юрисдикции
- `/ui/sources/{id}` — метаданные источника + список его чанков
- `/ui/chunks/{id}` — текст чанка, цитата, иерархия, сноски, ссылка на
  страницу оригинала в PDF (presigned URL с `#page=N`)
- `/ui/upload/source` — форма добавления источника: метаданные + файл PDF
  (тот же путь, что и `POST /sources`, через общий сервисный слой
  `app/api/services/sources.py`)
- `/ui/upload/chunks` — форма загрузки чанков: выбор источника + JSON-файл
  с массивом чанков (та же схема, что у `POST /sources/{id}/chunks`, через
  `app/api/services/chunks.py`); файл валидируется той же Pydantic-моделью
  `ChunkBulkCreate`, ошибки показываются на странице

Это единственные операции записи в веб-интерфейсе — редактирования или
удаления уже загруженного через `/ui/*` нет; для правок — напрямую в БД
или через API.

## Известные ограничения этого захода

- Парсинг PDF в чанки и понятийный слой/глоссарий — не реализованы (см. ТЗ).
  MCP-сервер реализован, но как часть этого же процесса (`app/mcp/`), а не
  отдельным сервисом — на CPX22 второй процесс ради тонкой read-only
  обёртки не оправдан, тот же аргумент, что и для `web` (см. выше).
- `POST /sources` сначала загружает файл в object storage, затем пишет
  строку в БД. Если запись в БД упадёт после успешной загрузки, в бакете
  останется файл-сирота без записи в `sources` — для внутреннего
  инструмента с ручной/скриптовой загрузкой это приемлемо; при
  необходимости лечится периодической сверкой бакета с БД.
